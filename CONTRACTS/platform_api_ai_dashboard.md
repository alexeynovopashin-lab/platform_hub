## Зачем один договор
Задание получили четыре проекта. Если каждый сделает своё, будет четыре API с разными правилами, четыре ИИ с разными правами и четыре дашборда с разными входами. Поэтому общее (формат, доступ, оболочка дашборда) ведёт ядро, а каждый проект описывает только свой раздел.

| Общее, ведёт ядро Event OS | У каждого проекта |
|---|---|
| Формат обмена: адрес `/v1/`, вид записи, поле «кто записал», паспорт факта, предложения вместо чужих правок, сигналы | Какие свои объекты отдаёт наружу и принимает |
| Доступ: люди, ключи-роботы, ИИ и вход «от имени» по одной модели прав; журнал | Какие галочки прав нужны в его разделе |
| Подключение ИИ: правила, гнездо поставщика, пометка «ИИ» | Где ИИ полезен в проекте и чего ему нельзя |
| Оболочка дашборда: один сайт, один вход, переключатель разделов, раздел «Платформа» | Свой раздел: какие числа и какие действия |
| Счётчики сервиса (живые ID, ошибки, расход облака и ИИ) | Свои счётчики, отданные по общему формату |
| — | Что живёт только на устройстве и наружу не выходит |

## 1. Формат обмена
Один для API, для подключаемых сервисов (`docs/PLATFORM_ARCHITECTURE.md` §4.11), для ИИ и для дашборда.
- **Адрес** `/v1/…`; общее (места, люди и роли, организации, события, журнал) — у ядра, объекты модуля — под его именем. Внутри версии поля не удаляются и не меняют смысл.
- **Запись** = номер, вид, время изменения и **«кто записал»**: человек, приложение, сокет (например, «Radio», «Calendar» — `event_os:BRIDGE_LIGHT_PLAN.md` §11), ключ-робот, ИИ. Незнакомые поля сохраняются и проходят дальше (§11).
- **Факт с паспортом**: значение + откуда + когда получено (погода, солнце, расчёт). Читатель видит, насколько факт свежий.
- **Чужое не правится, а предлагается.** Изменение объекта, у которого другой хозяин, приходит предложением с отметкой «кто предложил»; принимает хозяин (`event_os:BRIDGE_LIGHT_PLAN.md` §3, согласие получателя). Правило одно для партнёра, ИИ и соседнего проекта.
- **Наружу уходит сигнал, а не содержимое.** Вебхук и пуш говорят «у объекта X изменилось»; содержимое забирают по ключу с правами.
- **Журнал**: каждое действие ключа, ИИ и входа «от имени» записано, хозяин данных его видит.

## 2. Доступ
- **Ключ = сотрудник-робот** с теми же галочками, что у людей, не шире прав выдавшего, отзыв одним нажатием (так же в PR #16 хаба, §3.4).
- **ИИ = клиент API с правами того, кто его позвал** (`event_os:30_AI.md` §6), не больше. Меняет только через предложение с пометкой «предложил ИИ» и основанием (§20, §46), без скрытой памяти (§47), не выдумывает состояние (§54). Если студия сама включила «ИИ отвечает клиенту», это право выдал человек; сообщение помечено «ИИ».
- **Личные данные** (телефоны, переписка, чеки клиентов) — только по отдельной галочке.
- **Данные, которые живут только на телефоне** (сегодня так в Light Plan), сервер отдать не может. Как быть — развилка Алексею (ниже).

## 3. Подключение ИИ
Два пути, оба через тот же API и те же права:
1. **Встроенный помощник**: черновики текстов, «что изменилось», разбор входящего файла в черновик. Поставщик — гнездо в §4.11; PR #16 предлагает по умолчанию российского поставщика ради 152-ФЗ, ядро не возражает.
2. **Свой ИИ человека или студии** подключается ключом-роботом.
Чужие файлы, которые ИИ читает, могут содержать подложенные команды, поэтому ИИ, прочитав чужое, ничего не отправляет наружу без человека. Кто платит за ИИ — вопрос Алексею (PR #16, §9 п.6).

## 4. Общий дашборд
- **Один сайт, один вход** (ID → одноразовый код, `docs/PLATFORM_ARCHITECTURE.md` §2а; владельцу платформы — обязательно второй способ подтверждения), сверху переключатель разделов: **Платформа · Light Plan · BroniOS · Сайт студии · Event OS**.
- **Оболочка и раздел «Платформа»** — ядро: люди и организации, деньги, здоровье сервиса, ключи и ошибки API, расход облака и ИИ. **Разделы проектов** описывает и делает каждый проект.
- **Дашборд — тоже клиент `/v1/`**, в базы напрямую не ходит. Что видно в дашборде, то сможет и сторонняя программа с такими же правами; дашборд заодно проверяет API.
- **По умолчанию числа, а не содержимое.** Вход в кабинет студии «от её имени» — только для поддержки, с причиной, записью в журнал и уведомлением хозяину (так же в PR #16, §3.3).
- **«Подключать и настраивать пользователей» — по единому ID.** У всей платформы один ID по номеру телефона, отдельных ID у приложений нет: Алексей 08.10, A-009, дословно «у нас есть единая система ID по номеру телефона» (`DECISIONS.md`, запись 2026-10-08); раньше — `event_os:BRIDGE_LIGHT_PLAN.md` §1 (3.09, «ID адресует, аккаунт удостоверяет»). Дашборд подключает людей к этому ID: выдаёт роли и галочки, включает модули. Не решено только, может ли владелец платформы править чужую учётную запись (развилка «Что видит дашборд владельца» ниже).
- **Раздел Light Plan.** Приложение живёт на телефоне, поэтому его раздел — числа и настройки, а не данные фотографов: живые ID, активные за 7/30 дней, ошибки и расход погоды и облака, версии на телефонах. Состав — ответ Light Plan, Q-053 в `QUEUE/lightplan.md`.

## 4а. Два уровня: админка продукта и кабинет пользователя
Алексей 07:25: дашборд **заменяет** админку сайта и админку BroniOS («один каталог, два входа», 10.10), но уровней два и их не смешивают: «админка продукта» и «пользовательский личный кабинет, админка пользователя». Дальше вывод ядра, не слова Алексея.

| | Админка продукта | Кабинет пользователя (админка пользователя) |
|---|---|---|
| Кто | владелец сервиса (Алексей), позже сотрудники платформы по галочкам | владелец студии и её сотрудники; школа; фотограф; организатор |

| Что делает | включает модули и тарифы, продлевает пробный период, переводит на заглушку, выдаёт партнёрские ключи, рассылает новости | правит свой каталог, цены, фото, тексты сайта, роли сотрудников, выдаёт свои ключи-роботы и подключает свой ИИ |
| Вход к другому уровню | «от имени» пользователя как поддержка (см. ниже) | в админку продукта не входит никогда |

**Третья роль — поддержка (Алексей 07:26, дословно выше).** Платформа должна иметь доступ к кабинету пользователя, чтобы помогать: настройка, ремонт, исправление багов. Поддержка — это вы и, позже, сотрудники платформы по галочкам; в кабинет она входит «от имени» пользователя. Твёрдо (вывод ядра): каждое действие поддержки пишется в журнал с причиной и пометкой «поддержка»; поддержка не получает права больше, чем у хозяина кабинета; правки поддержки отменяются так же, как правки самого пользователя. Не решено, решает Алексей (развилки П1–П3 ниже).

Оба уровня — на одном сайте с одним входом по единому ID: что открывается после входа, решают роли человека. Переключатель разделов (Платформа · Light Plan · BroniOS · Сайт студии · Event OS) есть на обоих уровнях, но на уровне пользователя показывает только подключённые им модули.

**«У сайтов система сложнее» — три лица одного сайта студии:**
1. **Публичный сайт** для посетителей (страницы, цены, бронь) — не дашборд.
2. **Админка пользователя** — то, что сегодня `/admin/` сайта «Томсон»: студия правит цены, фото, видео, портфолио, тексты, позже темы, домен, SEO. Переезжает в кабинет пользователя.
3. **Админка продукта** — над всеми сайтами: темы оформления, домены и поддомены, тарифы, заглушка за неуплату, выдача шаблонов.
Сайт пишет в один каталог студии (`CONTRACTS/studio_catalog.md`) и с уровня пользователя, и с уровня BroniOS: «два входа» становятся двумя разделами одного кабинета, правило одного каталога сохраняется.

**Пока ядра нет, работающие админки не трогаем:** `/admin/` сайта и админка BroniOS остаются как есть, в кабинет пользователя переезжают, когда готовы вход, роли и журнал ядра.

## 5. Что каждый проект пишет в ответ (Q-050…Q-052)
Коротко, в своей очереди:
1. **Наружу и внутрь:** какие свои объекты отдаёт и принимает, примеры внешних сервисов.
2. **Только на устройстве:** что сервер не видит и видеть не должен.
3. **Раздел дашборда:** какие числа видит владелец платформы, какие действия может сделать, что ему видеть нельзя.
4. **ИИ:** где полезен в проекте, чего ему нельзя.
5. **Расхождения** с этим договором.

### Поддержка в кабинете пользователя (после слова Алексея 07:26)
- **П1. Как поддержка входит.** А — по запросу: пользователь нажимает «пустить поддержку» на срок (например, 24 часа), доступ сам закрывается (совет: так студия сама решает, когда к ней заходят) / Б — всегда может войти, но пользователь получает уведомление при каждом входе / В — всегда может войти без уведомления, только запись в журнале. Срочный ремонт, когда пользователь недоступен, при А невозможен; при Б и В возможен.
- **П2. Видит ли пользователь, что делала поддержка.** А — да, в журнале своего кабинета, каждое действие (совет; 152-ФЗ и доверие студий, закон не проверен) / Б — только факт входа / В — нет.
- **П3. Данные, которые живут на телефоне** (Light Plan: клиенты, съёмки). Сервер их не видит, значит и поддержка через кабинет — тоже. А — поддержка их не видит никогда; для ремонта пользователь сам отправляет отчёт без личных данных (совет) / Б — пользователь по своей кнопке отправляет копию с личными данными на время разбора / В — приложение присылает их серверу по запросу поддержки. Согласие адресата — `event_os:BRIDGE_LIGHT_PLAN.md` §3; Б и В требуют проверки закона о персональных данных.
